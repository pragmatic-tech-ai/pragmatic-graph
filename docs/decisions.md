# Engine design decisions — Plan 1 (durable storage foundation)

Decisions taken while executing Plan 1 (Project #1 item "[Engine] Plan 1 — durable storage foundation") against the living spec "[Engine] Pragmatic graph engine — living design". Each line: what was decided — why — cost if wrong. Later plans should treat these as the current contract unless the spec supersedes them.

## Execution rulings (R1–R34)

- R1 FormatKeys.Meta(name: string, ...qualifiers: TupleElement[]) — T10 needs a qualified meta key; varargs keeps the T5 call shape — cost if wrong: trivial rename.
- R2 Member ids are catalog-global (one id space across all concepts/aspects), assigned once, stable, never reused, starting at 1; id 0 is reserved for the implicit node-id column (Int64, non-null) present on every concept; an aspect-contributed member keeps its one id in every carrier — matches T5 "member 0 is node-id column" and T6 "same Id in every concept" — cost if wrong: renumbering before any real data exists.
- R3 IdAllocator.Next(txn: IWriteTransaction, clusterHint?: string): Promise<bigint> (persists Meta("nextBlock") through the txn) — the plan's sync signature cannot persist — cost if wrong: signature change in T12 only.
- R4 RowIndex caches decoded blocks per transaction (WeakMap keyed by txn), never across transactions — a shared cache would leak uncommitted or newer state into older snapshots — cost if wrong: perf only, revisit with commit-versioned cache.
- R5 Committer exposes UpdateCatalog(snapshot) (or GraphStore recreates it) so DefineSchema takes effect; implementer's call in T12/T13 — cost if wrong: small refactor.
- R6 `npm run typecheck` must also type-check test files (tsc -p tsconfig.json --noEmit in addition to the build config) — tsx does not type-check, so test type errors would otherwise go unseen — carried into Task 2 — cost if wrong: one script line.
- R7 Task 2 test asserts PrefixEnd(Encode([5n])) <= Encode([6n]) instead of strict < — FDB prefix-end of 0x15 0x05 is exactly 0x15 0x06 = Encode([6n]); plan value was wrong; exclusive end makes equality correct — cost if wrong: none.
- R8 owner rule "fix minors, never defer": carried into Task 3 dispatch as an extra item (Between returns a copy) so it is reviewed with Task 3's diff — cost if wrong: none.
- R10 (Task 6) Validation runs at Seal() (forward references between definitions allowed); Define* only records. Unknown parent/aspect/relationship target → UnknownType. An aspect named as a concept's parent → AspectAsParent; a concept named in a concept's aspect list or an aspect's include list → ConceptInAspectList; MultipleParents is reserved for API misuse that supplies more than one parent (e.g. same concept defined twice with different parents). Defining a name twice → new code DuplicateType (appended). — cost if wrong: error-code shuffle.
- R11 (Task 6) Concepts and aspects share one stable type-id space (assigned once in definition order from 1, never reused). PreOrderInterval exists for concepts only; ConceptsMatching returns concept type ids only. CatalogSnapshot.RequireInstantiable(name): number returns the concept's type id and throws AspectNotInstantiable for an aspect (UnknownType for unknown) — Task 12's CreateNode uses it. — cost if wrong: small API change.
- R12 (Task 6) Member 0: `CatalogSnapshot.NodeIdMember: MemberDef` static (Id 0, Name "$id", Kind Property, Type Int64, Nullable false, DeclaredBy ""); NOT included in EffectiveMembers. Member ids (properties, relationships, and edge properties) are catalog-global from 1. Add `CatalogSnapshot.Member(concept, name): MemberDef` lookup (throws UnknownMember — appended code) and `CatalogSnapshot.Names(): readonly string[]`-style enumeration as needed by Task 7 serialization. — cost if wrong: small API change.
- R13 (Task 6) Schema evolution: `CatalogModel.FromSnapshot(snapshot): CatalogModel` reproduces the definitions with their assigned type and member ids so new definitions can be added and re-sealed with ids stable (Task 7 Load and Task 13 DefineSchema rely on it). Version: an empty catalog has Version 0; each Seal() yields previous Version + 1 (FromSnapshot carries the version). — cost if wrong: Task 7 adjusts.
- R14 (Task 6) InvalidMember code accepted (property without Type, relationship without Targets, non-property edge property) — needed validation the plan omitted — cost if wrong: none.
- R15 (Task 7) CatalogStore.Save requires snapshot.Version === storedVersion + 1 (each Save persists exactly one Seal made from the loaded catalog via FromSnapshot) and writes it to Meta("catalogVersion"); otherwise throws CatalogError with new appended code VersionConflict. Load returns a snapshot whose Version equals the stored value (0 when empty). Reconciles plan "Save increments version" with R13 "Seal increments Version" and guards concurrent schema changes — cost if wrong: small.
- R16 (Task 8, supersedes R3) IdAllocator is constructed over the IKeyValueStore and reserves 4,096-id blocks in its OWN short store.Write (hi/lo): `static Open(store): Promise<IdAllocator>`, `Next(clusterHint?: string): Promise<bigint>`. A block, once reserved, is durable before any id from it is handed out, so a rolled-back caller transaction can waste ids but never duplicate them. Next must not be called from inside a Write on the same store (the single-writer mutex would deadlock) — Task 12 allocates ids before entering its group Write. Document this on the class. — cost if wrong: Task 12 call-order change.
- R17 (Task 8) PublicIdIndex.Bind/Unbind are async (conflict checks need reads) — accepted; RowIndex v1 handles partition 0 only and rejects others (row entries do not store partition; keys still carry it per seam 3) — accepted, multi-partition row index is a later plan — cost if wrong: small.
- R18 (Task 10) The node-id column (member 0, Int64) stores the internal id; to keep it a plain signed Int64 (and i64 in Rust) InternalId.Max becomes 2^63-1 (ids are allocated from 1 upward in 4,096 blocks, so the cap is never near) — change InternalId and its tests in Task 10 — cost if wrong: trivial.
- R19 (Task 10) Chunk number = slot / 2048 (bigint), slot-in-chunk = slot % 2048. Missing chunk + no delta → cell reads null. A delta holds at most one entry per slot (later write replaces), entries sorted by slot. WriteCell/ReadCell reject relationship members (properties and member 0 only) and type mismatches. Compactor writes the chunk with ChunkCodec.ChooseEncoding. Slot counter Meta("slots", typeId) is read/written through the caller's write txn (ColumnStore runs inside the committer's Write). Deleting a node = writing null to member 0 (slot not reused in v1).
- R20 (Task 10 fix) ColumnStore keeps a per-write-transaction delta cache (WeakMap keyed by txn → parsed sorted per-chunk delta state + dirty flag); WriteCell mutates in memory; `ColumnStore.Flush(txn: IWriteTransaction): void` serializes dirty deltas once and MUST be called before the write txn commits (Task 12 Committer calls it inside its group Write); reads in the same txn see cached state; Compactor goes through the same ColumnStore instance. Non-null enforcement for non-nullable properties in ColumnStore (member 0 exempt as the delete path). Compaction threshold policy belongs to Task 12. — cost if wrong: a Flush call forgotten = lost writes, so Task 13 durability tests must cover it.
- R21 (Task 11) Edge semantics: a (from, relationship, to) pair links at most once (Link of an existing pair → EdgeError DuplicateEdge); a relationship with Many !== true allows at most one outgoing edge per source (second Link → EdgeError CardinalityExceeded); unordered relationships use the empty position; ordered without After/Before appends after the current last; After/Before positions must belong to edges of the same (from, relationship) or → EdgeError UnknownSibling; Unlink of a missing pair → EdgeError MissingEdge. Out value = edge-property list (memberId u32 LE, value length u32 LE, single-value bytes per Task 9) sorted by memberId; In value = empty. Edge properties validated against relationship.EdgeProperties (unknown name / type mismatch / non-nullable null → error). Target type checking (to's concept matches Targets) is the Committer's job (Task 12), not EdgeStore's. Document the Out/In value layout in on-disk-format.md.
- R22 (Task 11) After+Before both given but not adjacent → EdgeError NotAdjacent; After >= Before → EdgeError InvalidOrder — "insert exactly between" is undefined otherwise — cost if wrong: callers pass one bound.
- R23 (Task 12) Conflict detection uses LOGICAL keys (field-level, per spec), built by a `ConflictKeys` class, never physical chunk/delta keys: Cell(internalId, memberId) in Keyspace.Columns; Node(publicId) in Keyspace.Ids (existence / create / delete); Adjacency(relationshipId, direction, nodeId) as a prefix range and Edge(relationshipId, direction, nodeId, otherId) in Keyspace.Edges. A Link/Unlink writes Edge keys under BOTH endpoints (Out on from, In on to), so a reader's AddRange over Adjacency(rel, dir, node) catches phantoms. DeleteNode writes its Node key, all its Cell keys and Edge keys of every removed edge. The Committer computes each batch's logical write-key set while applying it.
- R24 (Task 12) Snapshot registry: `Committer.RegisterSnapshot(): { readonly Commit: bigint; dispose(): void }`; committed write-key sets are retained back to the oldest registered snapshot (or only the latest when none is registered); Submit with a snapshotCommit older than the retained window → ConflictError (conservative). Submit with snapshotCommit > LastCommit → error.
- R25 (Task 12) Group commit: concurrent Submits form one group; validation in order (each against committed history after its snapshot AND earlier batches accepted in the same group); internal ids for CreateNode allocated via IdAllocator BEFORE the group's store.Write (R16); within one store.Write each batch is applied in order; if a batch fails semantically while applying (CommitError), abort that store.Write, reject only that batch, and re-run the remaining batches as a new group (ids already allocated are reused). Before the Write resolves: ColumnStore.Flush(txn) then AssertFlushed(txn) (R20). Commit numbers assigned in group order; each accepted batch → LogEntry(commit) + Meta("commit") = last. CommitApplied raised once per commit, in order, after the store.Write resolved.
- R26 (Task 12) Semantic checks raise `CommitError` with `CommitErrorCode` (UnknownNode, DuplicatePublicId, UnknownMember, NotAProperty, NotARelationship, TargetTypeMismatch, plus pass-through of EdgeError/CatalogError/ColumnStore errors wrapped with their cause): CreateNode uses CatalogSnapshot.RequireInstantiable; SetProperty member must be a property in the node concept's EffectiveMembers; Link `to`'s concept must IsA one of the relationship's Targets; DeleteNode removes the node's Out edges over its effective relationships and In edges over relationships whose Targets match its concept, nulls member 0, clears the row entry and unbinds the public id. Operations in one batch see the batch's own earlier operations (sequential apply in the txn).
- R27 (Task 12) WriteBatch.Serialize format: binary, documented in on-disk-format.md (Log keyspace section): u8 format version, u32 op count, per op u8 WriteOp + fields as length-prefixed UTF-8 strings; CellValue as u8 ValueType tag (0 = null) + single-value bytes (Task 9); LinkOptions with presence flags. Deserialize(Serialize(b)) deep-equals b.
- R28 (Task 12) Compaction policy: after applying a group, the Committer compacts any chunk whose delta exceeds `Committer.CompactThreshold = 512` entries within the same store.Write (ColumnStore exposes the pending entry count per touched chunk). Committer gets `UpdateCatalog(snapshot)` (R5).
- R29 (Task 12) Extent(typeId) conflict key (written by CreateNode/DeleteNode, read by concept scans) accepted — needed for ScanConcept phantoms; extra CommitErrorCodes accepted; empty read set never conflicts (blind writes) accepted. Required (non-nullable) properties: every node created in a batch must have all non-nullable properties set by the end of that batch → CommitError MissingRequired (to fix in Task 12 fix round). Task 13 must RegisterSnapshot before BeginRead and dispose it.
- R30 (Task 13) GraphReader/GraphTransaction open as: Committer.RegisterSnapshot() FIRST, then store.BeginRead(), then read Meta("commit") inside that KV snapshot and use it as snapshotCommit (>= the registered one, so retention covers it); dispose releases both. Reads are snapshot reads: a GraphTransaction does NOT see its own pending writes (flow-language semantics: no read-your-own-writes) — document on the class.
- R31 (Task 13) Read-set recording (R23/R29 keys): GetProperty → Node(publicId) (also when missing — catches a later create) + Cell(id, member); Neighbors → Node(publicId) + AddRange Adjacency(rel, dir, id); ScanConcept → Extent(typeId) for every matching type + Cell(id, member) per row yielded. Only GraphTransaction records; GraphReader does not.
- R32 (Task 13) DefineSchema: Load catalog in a store.Write, FromSnapshot → define callback → Seal → CatalogStore.Save, then Committer.UpdateCatalog. Each GraphTransaction captures the catalog Version at Begin; Commit when the catalog version changed since Begin → ConflictError. GraphStore.dispose(): await Committer.dispose() (waits in-flight group), dispose open readers, then the store; idempotent. On open: FormatMeta.Initialize on an empty store, FormatMeta.Verify otherwise; CatalogStore.Load; Committer.Open resumes LastCommit.
- R33 (Task 13 fix) ordered Link with AfterSibling/BeforeSibling resolves the sibling position via the sibling's In range (In keys already carry the position; O(in-degree of the sibling), 1 for trees) and the neighbour via a bounded forward Scan (limit 2) from that Out position — no on-disk format change; plain append (no siblings) stays O(out-degree) until a later plan adds a tail index — cost if wrong: perf only.
- R34 (Task 13 round 2) the KV Scan defect (write-txn Scan on both backends and memory read-txn Scan materialise the whole range before applying limit) is fixed now inside Task 13 round 2 — R33 depends on it and the owner rule is no leftovers — lazy merge of a base iterator with the sorted pending list, stopping at limit; conformance case counting base reads via a probe.

## Final-review rulings (F1–F9)

- F1 Ordered positions: replace FractionalPosition with logarithmic-growth fractional indexing (integer part with a length prefix + fraction, base-256 or base-62 digits; append/prepend grow O(log n); between-insert may grow ~1 bit per insert). Positions stay opaque, non-empty, never ending in 0x00 (state the validity rule in the format doc). Add `Reverse?: boolean` to IReadTransaction.Scan (both backends, conformance cases incl. own-writes merge in reverse) and use it for O(1) tail lookup on append. Portable maximum encoded key size = 511 bytes, enforced in both backends with a typed error (KeyTooLong) and a conformance case. Public ids may not contain U+0000 (reject) so a 400-byte id always fits. If a between-insert position would push an Edge key past the limit, EdgeStore renumbers that (source, relationship) list evenly inside the same txn (writing conflict Edge keys for every rewritten edge) — supersedes the plan's "never renumber" (positions are internal). Bulk-append benchmark: 20k appends to one list in one batch must be ~linear (linearity ratio check).
- F2 LmdbStore opens with overlappingSync: false (explicit, all platforms) so Commit resolves only after the data is durable; test asserts the option.
- F3 (amends R30/R24) Only GraphTransaction registers a committer snapshot; GraphReader opens a KV snapshot only.
- F4 Commit log is a self-sufficient changefeed: DefineSchema goes through the Committer as a log entry kind (SchemaChange carrying the serialized catalog delta or full catalog JSON + resulting version) with a commit number and CommitApplied; every log entry records the catalog version it was validated against and the internal ids allocated for its CreateNode ops (so replay is deterministic); a transaction's catalog-version check happens inside the group against the group's catalog (fixes the early-check race). Expose `GraphStore.ReadChanges(afterCommit: bigint): AsyncIterable<ICommitApplied>` over the log. Format version stays 1 (unfrozen) — update the doc.
- F5 Partition seams: slots key → Meta("slots", partition, typeId); row-index entries carry the partition: (partition u32, typeId u32, slot u32) little-endian, 12 bytes, unassigned iff all three 0xFFFFFFFF; row index is global (keyed by id block only — RowBlock(block)), document. Catalog TypeDefinition gains `Placement` (enum Replicated | Partitioned, default Partitioned for concepts) and optional `AggregateRoot` (concept name) — additive JSON, validated (AggregateRoot must name a concept).
- F6 Write amplification: RowIndex keeps dirty blocks per write txn and writes each once at Flush (same Flush/AssertFlushed discipline as ColumnStore; Committer flushes both); row block size becomes 512 entries (≈6 KB) independent of the 4,096-id allocation block (sparse: missing block = unassigned); IdAllocator reserves 16 blocks per allocator Write (constant), handing them out locally.
- F7 ReadSet ranges kept sorted and coalesced, binary-searched; full-column scans record one coarse conflict key Column(typeId, memberId) (writers of a Cell also write Column(typeId, memberId)); Neighbors sweeps keep per-node Adjacency ranges but benefit from coalescing.
- F8 Error surface: `GraphError` base class with `GraphErrorCode` (InvalidArgument, NotFound, Conflict, Disposed, Corrupt, SchemaViolation, KeyTooLong, ...); CommitError/CatalogError/EdgeError/ChunkCodecError/PublicIdTooLongError extend or wrap it; reads raise the same codes writes use for the same mistakes; index.ts exports GraphError + codes.
- F9 Minors: DeleteNode on ordered high in-degree uses known positions (no re-scan per unlink); Neighbors variant without properties used by GraphReader.Neighbors and DeleteNode; MemoryStore commit copy-on-write per leaf/chunk instead of whole keyspace copy; LMDB exclusive lock file to prevent two writer processes (clear error); OpenLmdb options (MapSizeBytes, MaxReaders); BeginRead reuses a native read txn when no commit happened since; DefineSchema cost noted (per-definition keys deferred — record in a docs/format note, not code); format doc gaps (named DB per keyspace with memcmp order, delta slot = slot within chunk, list of intentionally partition-free keys); hoist template-literal messages in ChunkCodecError/FormatVersionMismatchError; deleted-node cells: DeleteNode nulls all property cells (not just member 0) — slot reuse stays a documented follow-up in the format doc; ColumnStore linearity base raised to >= 30 ms small run; MemoryStore.KeyspacesRebuilt doc says not part of IKeyValueStore; Rust-spec note "encoders must be canonical" in the format doc.

## Engine core consolidation rulings

- R35 (Consolidation Task 1) Node owner is a separate `(IdsTag.Owner, id)` key in the Ids keyspace holding UTF-8 text, written only for a non-empty owner, deleted by `PublicIdIndex.Unbind` with the id directions; absent reads as `''` — avoids a per-node cost for ownerless nodes and keeps the node-id column and row index unchanged. `Unbind` deletes the owner key unconditionally, without reading it first: for an ownerless node that is one blind delete of an absent key per DeleteNode, accepted because a read to skip it would cost a Get on every delete, owned or not (final review) — cost if wrong: a format change to inline the owner into the row, before format freeze.
- R36 (Task 1) Owner is create-time only and covered by the existing `Node(publicId)` conflict key (no new logical key); `OwnerOf`/`ConceptOf` record `Node(publicId)` also when missing — owner cannot change, so a read can only be invalidated by create/delete of the node — cost if wrong: owner change later needs its own write key.
- R37 (Task 1) `CreateNode` takes `ICreateNodeOptions { ClusterHint?, Owner? }` instead of a positional hint; the serialized CreateNode flag byte becomes a bit set (bit 0 hint, bit 1 owner, other bits rejected), format version stays 1 (unfrozen) — cost if wrong: none for stored data, only logs written by earlier builds in dev stores.
- R38 (Task 1) `ScanNodes` walks the node-id column of each matching concept (live slots in slot order, so nodes deleted in committed history are absent) and records `Extent(typeId)` per matching type, no per-node keys; `EstimateCount` sums slot counts (includes deleted slots, an upper bound) and records nothing — cost if wrong: a planner relying on exact counts over-estimates after deletes.
- R39 (Task 2) Predicates evaluate with internal three-valued logic (True/False/Unknown), collapsed to false only at the top of `NodeEvaluator.Matches`; Unknown arises only from a null/absent member or null literal, `Not(Unknown)` stays Unknown, And/Or follow Kleene logic (False AND Unknown = False, True OR Unknown = True), `In` over a null member is Unknown — cost if wrong: an index or scope relying on `Not(cmp)` matching null rows must add an explicit `Or([Not(cmp), IsNull])`.
- R40 (Task 2) Cross-type comparisons and any comparison involving NaN are plainly False (not Unknown), so `Not` of them is true; Int64 vs Float64 compare exactly (mathematical value, not via lossy conversion); Date and DateTime are distinct types; DateTime compares by Micros only (zone ignored, unlike `Equals`); Duration supports only Eq/Ne, every other op is false — cost if wrong: a `Not(Compare)` over a mixed-type column matches rows a SQL user would expect excluded.
- R41 (Task 2) Strings compare by UTF-8 bytes (`Buffer.compare`), not JS UTF-16 code-unit order, so astral characters sort after U+FF5E as TupleCodec does — cost if wrong: partial-index range scans and predicate evaluation would disagree on astral text.
- R42 (Task 2) Predicate JSON is `{ Kind: <number>, ...fields }` with sets as sorted arrays and non-JSON cell values as single-key tagged objects (`{ Int64: "5" }`, `{ Float64: "NaN" }`, `{ Date }`, `{ DateTime }`, `{ Duration }`), documented on `PredicateCodec`; `NodeEvaluator.Matches` rejects any non-node-local tree up front (no short-circuit skipping) — cost if wrong: persisted index/scope definitions need a migration if the shape changes.
- R43 (Task 3) Index validation in this task is limited to: unique names (DuplicateType), `On` names a known concept or aspect (UnknownType), at least one member, members distinct properties effective on `On` (UnknownMember when absent or a relationship, InvalidMember for empty or repeated); it lives in the single method `CatalogSnapshot.ValidateIndexes` where Task 6 adds Where-node-local and Duration-not-indexable rules — cost if wrong: an index created before Task 6 lands may need to be rejected on the next plan.
- R44 (Task 3) Index ids are a separate counter (`NextIndexId`, from 1), member lists are stored as member ids (so a retyped member makes an index on it be rebuilt: removed plus added), and `IndexesOn(concept)` returns the indexes that apply to a concept (declared on it, an ancestor, or a carried aspect) while `Indexes()` is every index — cost if wrong: Task 6 may want exact-`On` lookup, a one-line filter.
- R45 (Task 3) `CatalogPlanner.Plan` returns the stored snapshot only when the whole new catalog is canonically identical to it; a change the Diff does not describe (Nullable false to true, concept Options, a member moving declaring type, index-free hierarchy details) yields a new version with `Diff.IsEmpty` true, so consumers must key off `Catalog !== stored`, not `Diff.IsEmpty`, to decide whether to persist — cost if wrong: a caller that skips persisting on `IsEmpty` would lose a nullability or placement change.
- R46 (Task 3) Members are matched old to new by (Name, a concept both are effective on), falling back to the same-named declaring type for an aspect no concept carries; `RemovedMembers` lists, per still-existing concept, every old effective member id that concept no longer has (also on a hierarchy change that drops an inherited member), and nothing for removed types (their data goes with `RemovedTypes`); edge-property ids follow their member and any edge-property change retypes the member; a type changing between concept and aspect is removed plus added — cost if wrong: column cleanup that expects per-type member lists for removed types must derive them from `RemovedTypes`.
- R47 (Task 3 review fixes) `ICatalogPlan.Changed` (true iff `Catalog !== stored`) is the persist signal, never `Diff.IsEmpty` (R45); member matching tries every concept a new member is effective on and takes the first compatible, unused old member, so a member hoisted from two siblings to a shared parent keeps exactly one old id (the first compatible sibling's) and the other sibling's old id is reported in `RemovedMembers` (single-id limitation: a member id is catalog-global, so two old columns cannot merge) — cost if wrong: the data of the losing sibling is dropped rather than merged. Members removed from a kept aspect that no concept carries are reported with `Type` = the aspect name; carried aspects report per concept (R46).
- R48 (Task 4) `Committer.SubmitUpgrade` runs alone in its group (queued as exclusive work, like `SubmitSchema`) and plans against the committer's catalog at its turn; it persists the new catalog, purges, writes `Meta("schemaVersion")` and appends an Upgrade log entry (kind 3) in ONE `store.Write` iff `ICatalogPlan.Changed` (R45/R47), never keyed off `Diff.IsEmpty`; when nothing changed it rewrites only a differing `Meta("schemaVersion")` (decided by a read first, so an unchanged load takes no write transaction), returns `{ Commit: LastCommit, Changed: false }`, consumes no commit number and raises nothing; a planning `CatalogError` rejects only the upgrade, and a `Version` that is not well-formed UTF-16 (lone surrogate) is `InvalidArgument` so the stored UTF-8 round-trips exactly; the first upgrade of an empty store plans against the empty catalog — cost if wrong: a version-only change that should be visible on the changefeed would need its own log kind.
- R49 (Task 4) Discard rules, exactly: (a) a removed concept loses every node (row, public-id binding, owner, both keys of every edge incident to it under the OLD catalog's outgoing and incoming relationships) and its whole `(partition, typeId)` column and delta range plus `Meta("slots")`; (b) a member a surviving concept no longer has (`RemovedMembers`: removed, retyped or no longer inherited) loses, for that concept only, its column range (property) or every edge from that concept's nodes (relationship); members reported against an uncarried aspect hold no data and are skipped; (c) an edge into a surviving concept's node is removed when the new catalog's relationship with that id no longer accepts the concept or no longer exists (this covers hierarchy changes of the concept or of an ancestor, not only `ChangedHierarchy` entries); (d) a surviving concept's node is removed iff it has a null cell for a non-nullable property that is effective on the concept in the new catalog but was not effective on it under the same id before — a new or retyped member (every node lacks it) or a kept member newly inherited (only nodes without a value go; with the purge invariant that is all of them, the check still reads the column) — while properties already effective and non-nullable under the same id are not checked (every live node has a value); a removed node of a surviving concept has every cell that can still hold a value nulled (slots are not reused). Everything is collected first with the OLD catalog index, edges deduplicated by (relationship, from, to, position), then removed; the compaction policy and Flush/AssertFlushed run as in a batch group (R20, F6) — cost if wrong: a rule that keeps data the new catalog cannot describe leaves orphans that a later id-stable change could resurface.
- R50 (Task 4) The purge's logical write keys (R23) form the Upgrade commit's history entry: `Node(publicId)` and `Extent(typeId)` per removed node, `Cell(node, member)` plus `Column(typeId, member)` for member 0 and every property of a removed node, a `Cell` key per live node and the `Column` key of each dropped column, `Extent` of every removed concept, and both `Edge` keys of every removed edge; transactions begun before the upgrade also fail on the catalog version (F4), so the keys guard only submitters that skip the version check — cost if wrong: none for GraphTransaction, which always checks the version.
- R51 (Task 4) An Upgrade log entry carries the schema version and the full resulting catalog but not the discarded data (`ICommitApplied.SchemaVersion` and `Catalog`; `Batch` empty): the discard is a deterministic function of the previous and the new catalog, so a replay re-runs `DataPurger`; `IPurgeStats` (nodes, non-null values, edges) is returned by `DataPurger.Purge` for diagnostics and tests but not surfaced on `IUpgradeCommit` — cost if wrong: a changefeed consumer that cannot re-run the purge would need the removed ids added to the entry, an additive change before format freeze.
- R52 (Task 4 review) The purge collects its node, edge and dropped-column lists in memory before writing (R49), so one upgrade holds O(removed nodes + removed edges) entries; a streamed purge (batched collect/remove passes, still inside the one upgrade Write) is future work for concepts with millions of nodes. The upgrade write-failure path is covered by a test seam that replaces the committer's private `purger` field by cast (no production hook) — cost if wrong: a very large discard needs memory proportional to what it removes.
- R53 (Task 5) Seed synchronization runs inside the upgrade's one `store.Write`, after the purge, whenever the description's `Version` differs from the stored `Meta("schemaVersion")` or the catalog changed (an upgrade with the same version and an unchanged catalog still takes no write); `SeedSynchronizer` builds one `WriteBatch` against the post-purge state (unlinks of overwritten nodes' out-edges, deletes of previously seeded ids missing from the seed, creates, property sets, links in seed array order) and the committer applies it with `BatchApplier`, so seeded data obeys every batch rule. A seed node present with a different hash, or a runtime node holding a seed id, is overwritten: every effective property (absent ones null; a non-nullable absent one is `CommitError MissingRequired`), out-edges replaced — CORRECTED (final review, spec §4.4 dev loop): an overwrite writes only what differs from the stored node, so re-seeding data a connector write-through already put in the engine is a no-op: a property is set only when its stored value differs (same type and value; floats by Object.is, temporal values by Equals; an absent effective property counts as null and is set to null only when not already null; a non-nullable absent one is still MissingRequired; a seed property that is not an effective property is still emitted so the batch fails on it), and a relationship's out-edges are unlinked and the seed links re-added in seed order only when they differ (ordered: the same sequence of targets with equal edge properties; unordered: the same targets with equal edge properties; absent edge property = null) or point at a node the same batch deletes (a recreated or removed seed node); matching relationships keep their edges and positions; a differing owner is `CommitError InvalidValue` (owner is create-time; checked before the concept, so it also fails a concept change); a differing concept deletes and recreates the node (seed wins; seeded incoming links are restored by R55, runtime incoming edges are lost). - R57 (Task 6) Index maintenance runs in `BatchApplier` at the end of each batch, per node, like MissingRequired (R29): a node is tracked when the batch creates it (on a concept with indexes), deletes it, or sets a member some applicable index reads (a key member or an effective property its `Where` names); its entries are read from storage at first touch and recomputed from the post-batch values at the end, then every removed entry is deleted before any added one is unique-checked and put (so values swapped between nodes in one batch do not collide). - R62 (Task 6 review) Index ranges over a completed tuple prefix `p` use the FoundationDB tuple-range convention `[p, p ++ 0xFF)`, never `[p, PrefixEnd(p))`: a string element ends in `00` and an embedded NUL encodes as `00 FF`, so `PrefixEnd` of the encoding of "ab" would also cover "ab\u0000x" (false unique violations, wrong equality seeks); every real extension of `p` continues with a type code below `0xFF`. Otherwise `WriteCoordinator.Run`: start the timer (ONE deadline bounds Prepare, every connector call and the reverts), `Committer.Prepare` with the same timeout (so the coordinator deadline is never later than the reservation's) raced against the deadline — at the deadline the caller gets ConnectorError(Connector `engine`, Phase `Prepare`, appended to ConnectorPhase) and the prepared commit is aborted whenever Prepare still resolves — then Begin each participant sorted by name, Apply each, Commit each — one call at a time, never inside `store.Write` (a connector may commit to the same store meanwhile) — then `Finalize`. An engine rejection at Prepare (ConflictError, CommitError, GraphError) and the gate's AccessError are rethrown as-is: no connector began. Any connector throw or the timeout: Abort the prepared commit first (its keys free at once), then Revert every connector that began in reverse Begin order, committed ones included (compensate), and throw `ConnectorError` (GraphErrorCode.ConnectorFailed = 13; `Connector`, `Phase` Begin/Apply/Commit/Finalize/Prepare, `cause`); an error escaping that is not a ConnectorError (an engine bug) is wrapped as one for the call last started. A failed Finalize (ConflictError after a schema change or upgrade invalidated the reservation, I/O, Disposed) reverts all and throws ConnectorError with Connector `engine`, Phase Finalize, cause the engine error. Revert errors are collected and the cause becomes `AggregateError([original, ...revertErrors])`, never swallowed. Reverts are awaited only until the deadline: a revert still pending at the deadline, and every revert not yet started then (started at once, concurrently, rather than queued behind a hung one), finishes on the late path and reports its failure on `ConnectorRevertFailed`, so the caller is answered promptly. Timeout: the caller is answered at the deadline with Phase and Connector of the call in flight (cause a GraphError ConnectorFailed naming the timeout); calls not yet made are not made; connectors whose calls returned have their reverts started before the throw (past the deadline they are not awaited, see above); the hanging connector is reverted only once its call settles (a late Begin's transaction is reverted when it arrives; a Begin that fails began nothing), and a failure of that late revert is raised on `GraphStore.ConnectorRevertFailed` (a ConnectorError with the hung call's connector and phase; for a late revert of a connector that was NOT the hung one, the reverting connector's name with the phase of the call that FAILED the write-through — the caller's ConnectorError.Phase — not that connector's own phase, as the test `a revert hanging at the deadline finishes on the late path` pins) — the only place left to report it; a throwing subscriber there is ignored (detached path). Late reverts are not awaited by dispose(). Late reverts themselves are not time-bounded (nothing waits for them). No on-disk change — cost if wrong: a connector that commits remotely but is never reverted on an engine failure leaves the two stores disagreeing with no signal; routing by the target instead of the source would write cross-model edges into the wrong system.
